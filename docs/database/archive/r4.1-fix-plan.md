# R4.1 — Fix the R4 history-capture migrations (v24→v28)

## Context

R4 ("make history capture real") was merged to `main` as PR #54 (merge `8b8578a`, feature commit `1fd2131`) with the **CI emulator job failing** (run 36456770265: 5 failures). The implementing agent only ran JVM unit tests, which never execute `Migration24To28Test` (it is an instrumented test). A review of the merged code found one bug that breaks every upgrade, missing triggers on fresh installs, several data-loss paths that break `AGENT.md` rules 1 and 3, a way for migration 25→26 to abort, and broken tests/schema files.

Intended outcome: R4 migrations that upgrade a v24 database without losing data and without crashing, triggers present on fresh installs too, schemas 25–27 exported, and the emulator CI job green.

**How the fix is delivered:** edit `MIGRATION_24_25`..`MIGRATION_27_28` **in place** (no v29). This is allowed by `AGENT.md` rule 6 because no build has ever reached a field device (Q6). It is also required: once 27→28 has dropped a column, no later migration can recover that data. The PR description must say the R4 migrations were edited in place and why.

Branch: `fix/R4.1-migration-hardening` (created locally from `main` @ `8b8578a`).

## Work items (in order)

### 1. Blocker: `identifier_types` column name mismatch
`IdentifierType.validationRegex` has no `@ColumnInfo`, so Room expects `validationRegex` (see `28.json` createSql), but `MIGRATION_24_25` and `IdentifierTypeSeed` use `validation_regex`. Room's post-migration validation rejects every upgraded DB → `MIGRATION_FAILED` on every device upgrading from v24.
- Add `@ColumnInfo(name = "validation_regex")` to `validationRegex` (rule 8: snake_case).
- Regenerate `28.json` (`./gradlew :android:database:assembleDebug` / kapt/ksp schema export) and confirm createSql now says `validation_regex`.

### 2. Triggers missing on fresh installs
The three R4 triggers (`trg_animal_identifiers_unique_active`, `trg_animal_identifiers_tag_permanence`, `trg_animal_group_memberships_single_open`) are only created inside the migrations; `SEED_CALLBACK` never creates them.
- Extract each trigger's DDL into a private function/constant in the `BeefTechDatabase` companion (they already use `CREATE TRIGGER IF NOT EXISTS`).
- Call them from the migrations (unchanged placement) and from `createLookupTriggers(db)` so both `onCreate` and `onOpen` install them.

### 3. Data loss (rules 1 and 3)
- **24→25 drops identifier rows whose type isn't seeded** (`WHERE identifier_type IN (SELECT code FROM identifier_types)`, ~L2360). Repair instead: after `IdentifierTypeSeed.execute(db)`, run `INSERT OR IGNORE INTO identifier_types (code, name) SELECT DISTINCT identifier_type, identifier_type FROM animal_identifiers`, then remove the `WHERE` filter so every row is copied.
- **Snapshot before any legacy column is dropped.** At the very start of `MIGRATION_26_27` (it is the first migration that drops a column — `parentId`), add:
  `CREATE TABLE legacy_animals AS SELECT animalId, tagNumber, oldTagNumber, temperatureNumber, referenceNumber, massKg, age, condition, photoPath, videoPath, animalGroupId, parentId FROM animals`
  This keeps: `condition` on animals with no `massKg` (`weight_kg` is NOT NULL, so 25→26 can't store it), legacy identifier values skipped because a different active identifier exists, unresolvable `parentId`, `age`, and duplicate tags from item 4. Not a Room entity → tests need `validateDroppedTables = false` (AGENT.md trap).

### 4. 25→26 aborts on duplicate legacy tags
`INSERT OR IGNORE` does not suppress the tag-permanence trigger's `RAISE(ABORT)`. The old `index_animals_tagNumber` was not unique, so two animals can share a `tagNumber` → whole migration aborts.
- In the TAG backfill (~L2418), additionally exclude a `tagNumber` that (a) appears on more than one animal (`GROUP BY tagNumber HAVING COUNT(DISTINCT animalId) > 1`) or (b) already exists as a `TAG` for a different animal in `animal_identifiers`.
- Excluded values are assigned to **no animal** (user decision) and survive in `legacy_animals` (item 3). Document this in the PR and in `docs/database/r4-implementation-plan.md`.

### 5. Deterministic dam resolution in 26→27
Current fallback (`SELECT ai.animal_id FROM animal_identifiers ai WHERE ai.identifier_value = a.parentId LIMIT 1`) matches any identifier type and is non-deterministic.
- Match only `identifier_type = 'TAG'`, only when exactly one distinct `animal_id` matches, and never when the result equals `a.animalId` (no self-parentage). Otherwise `dam_id` = NULL (value kept in `legacy_animals`).
- Also guard the direct-UUID branch against `parentId = animalId`.

### 6. Keep FK checks as they are
Leave the whole-DB `PRAGMA foreign_key_check` at the end of each migration: it's the house convention (rule 10, same as 14→16, 22→23, 23→24) and FKs are enforced at runtime, so a real v24 DB has no pre-existing violations. The CI "FK violations after 24->25" failure is a **test fixture bug** (item 7), not a field crash.

### 7. Schemas and tests
- **Export 25.json, 26.json, 27.json** (rule 11). Room only exports the current version; derive them from `24.json`:
  - 25 = 24 + `animal_weights.body_condition_score TEXT` + `identifier_types` entity + `animal_identifiers` FK to `identifier_types` (copy entity blocks from the regenerated `28.json` where unchanged since 25).
  - 26 = 25 (schema-identical; triggers aren't in Room JSON), version bumped.
  - 27 = 26 with `animals.parentId` replaced by `dam_id`, `sire_id` (+ FKs + indices, exactly as the 26→27 DDL).
  - Sanity check: 27 minus the columns 27→28 drops must equal `28.json`'s `animals` entity field-for-field. Take `identityHash` for each from the file content consistently (MigrationTestHelper uses the JSON to create DBs and validate tables; it doesn't recompute the hash).
- **`Migration24To28Test` fixtures:** insert `devices` (`DEV-001`) and `breeds` (`Bonsmara`) rows at v24 before the animals (their absence caused the FK failure). Meet rule 12: ≥2 rows per affected table; assert row counts, key values, GUIDs unique and non-empty. Pass `validateDroppedTables = false` where 26→27 creates `legacy_animals`.
- **New tests** (in `Migration24To28Test`):
  1. unknown identifier type at v24 survives to v28 and is registered in `identifier_types`;
  2. two animals with the same legacy `tagNumber` → migration completes, neither gets that TAG, both values are in `legacy_animals`;
  3. `condition` with NULL `massKg` → preserved in `legacy_animals`;
  4. unresolvable / ambiguous / self `parentId` → `dam_id` NULL, value in `legacy_animals`;
  5. fresh DB built via `Room.inMemoryDatabaseBuilder(...).addCallback(BeefTechDatabase.SEED_CALLBACK)` has all five R4 triggers (`SELECT name FROM sqlite_master WHERE type='trigger'`);

- **`DatabaseMigrationPhase3And6And7Test`**: fails with `FOREIGN KEY constraint failed (code 787)`. Investigate — likely a fixture still inserting something that now violates an R4 FK (e.g. `identifier_type` not in `identifier_types`, or parent linkage after `parentId`→`dam_id`). Fix the fixture, not the schema, unless it exposes a real bug (then report it).

## As implemented

- **Unknown identifier types** (item 3): Known legacy types are remapped (`RFID` → `TRANSPONDER`, `OLDTAG`/`TAG_OLD` → `OLD_TAG`). Anything else is copied to `quarantine_animal_identifiers` before the rebuild. Unrecognized types are not added to `identifier_types`.
- **Triggers**: There are five triggers (`trg_animal_identifiers_unique_active`, `trg_animal_identifiers_unique_active_update`, `trg_animal_identifiers_tag_permanence`, `trg_animal_group_memberships_single_open`, `trg_animal_group_memberships_single_open_update`). All five are defined once in `createHistoryTriggers()` and called from `MIGRATION_24_25`, `MIGRATION_25_26`, and `SEED_CALLBACK`.
- **Membership backfill**: Migration 25→26 skips any animal that already has an open membership in any group (`NOT EXISTS (SELECT 1 FROM animal_group_memberships agm WHERE agm.animal_id = animals.animalId AND agm.left_at IS NULL)`). Its legacy `animalGroupId` is kept in `legacy_animals`.
