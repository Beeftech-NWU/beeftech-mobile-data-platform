Chapter 1Introduction

What you are working on

BeefTech is an offline-first Android app for feedlot management, livestock traceability and farm data capture, plus a Kotlin/Ktor server that the phones sync into. Field teams often work for days without signal, so the phone is the system of record until the server has confirmed each record.

This manual is for the people who build and maintain the platform. It explains how the code is organised, how data moves from a phone to the server, the rules that keep field data safe, and step-by-step recipes for the changes you will make most often. The User Manual describes the same app from the point of view of the people who use it; read its Chapter 3 (working offline and syncing) for the user-facing view of what this manual describes in code.

App developers

Feature modules, Compose screens, the encrypted Room database and the sync workers. Chapters 3–6, 9, 10.

Backend

Server developers

The Ktor API, its SQLite schema, auth, scoping, email and reports. Chapters 5–10.

First build

  1. Clone the repository and open a terminal in its root.
  2. Tell Gradle where the Android SDK is. local.properties is git-ignored, so every machine needs its own: 
    echo "sdk.dir=$HOME/Android/Sdk" > local.properties   # macOS: $HOME/Library/Android/sdk
  3. Check the toolchain. Daemon JVM: Compatible with Java 17 means the pin was satisfied: 
    ./gradlew --version
  4. Run the same fast checks CI runs: 
    ./gradlew testDebugUnitTest test

Running the backend

./gradlew :backend:api:run -Dbeeftech.seed.dev=true
curl http://localhost:8081/          # BeefTech Backend API is running
  • Listens on 0.0.0.0:8081 (or $PORT).
  • Creates its SQLite database at ./data/beeftech-backend.db, relative to the working directory, and keeps calf photos in a media/ folder next to it.
  • Seeds reference data (diseases, treatment types, cost types) and the feed crib reading codes on every start. Values an admin deactivated stay deactivated.

Chapter 3Architecture

The big picture

Every record is written to the encrypted local database first and queued. Sync is a separate, retryable step that never deletes local data because a request failed.

  1. Capture. Compose screens validate at the point of entry.
  2. Encrypted local write. The repository writes the record to the SQLCipher database with its audit metadata (record GUID, capture time, device ID, GPS where available, user ID).
  3. Queue. A row in pending_sync (or the record's own sync_status) says it still has to be sent.
  4. Sync. A WorkManager worker posts the waiting records in a batch with the session's JWT.
  5. Acknowledge. The server upserts each record by GUID and stamps the submitter and site from the token. The phone marks the record SYNCED and clears its queue row.
  6. Check-in. Separately, DeviceCheckInWorker downloads reference data and the sync policy and uploads the phone's security events.

Layers inside a feature

Feature modules follow the same shape. :android:feed-crib is the newest and cleanest example; use it as your template.

android/feed-crib/src/main/java/com/beeftech/feedcrib/
├── data/
│   ├── FeedCribApiClient.kt        # Ktor client: one method per endpoint, returns Result<T>
│   ├── FeedCribNetworkModels.kt    # @Serializable request/response DTOs
│   ├── FeedCribMappers.kt          # DTO ⇄ Room entity
│   ├── FeedCribRepository.kt       # save locally, queue, try to send, reconcile results
│   ├── FeedCribCaptureContext.kt   # device ID, capture time, GPS for a new record
│   └── SlotAllocator.kt            # pure domain logic, unit-tested on its own
├── ui/                             # Compose screens and components
├── viewmodel/                      # ViewModel + factory
└── worker/FeedCribSyncWorker.kt    # CoroutineWorker: retries until nothing is waiting
  • UI only talks to its ViewModel. It collects StateFlow/Flow and sends user intents.
  • ViewModels talk to repositories, never to DAOs or HTTP clients.
  • Repositories own the business rules: validation, the local write, queuing, calling the API client and applying per-record results. Their collaborators (DAO, API client, clock, user ID, time zone) are constructor parameters so tests can pass fakes.
  • Entities and DAOs always live in :android:database, even when only one feature uses them, because there is one database and one migration chain.
  • API clients take a TokenProvider, default their baseUrl to BackendConfig.baseUrl, and report a 401 with tokenProvider.reportUnauthorized(…).

App start-up

BeefTechApplication.onCreate runs before anything else, including when WorkManager starts the process in the background for a scheduled sync:

  1. Configures BackendConfig from BuildConfig.BACKEND_BASE_URL. This must happen before any API client is built.
  2. Creates EncryptedSessionStore and registers it with TokenProviderRegistry and CurrentUserIdRegistry, so background workers can get a token and the current user without an Activity.
  3. Registers SyncPolicyActivityGuard, which enforces the Day-7 lock in every Activity, including the farmer registration Activities started outside MainActivity.
  4. Calls ScheduledSyncScheduler.schedule: two daily periodic jobs at 05:00 and 18:00 that run ScheduledBatchSyncWorker. It also cancels the legacy 15-minute periodic jobs.
  5. Starts SunlightBrightnessController, which raises screen brightness in strong sunlight.

MainActivity then opens the encrypted database on a background thread through DatabaseProvider.initialize(context, passphrase), seeds one demo calf (tag Blu0000001) if it does not exist, and shows PolicyAwareAuthGate: the PIN login (AuthGate), a device check-in, then SyncPolicyGate, which re-evaluates the unsynced-data policy every 60 seconds.

Demo passphraseMainActivity opens SQLCipher with the hard-coded passphrase beeftech-demo-passphrase. It must be replaced with the Android KeyStore–backed key (DatabaseKeyProvider / SecureDatabaseInitializer in database/security/) before production. Changing it on an existing install needs a re-key step, or the phone can no longer open its own data.

Chapter 4The local database

Room and SQLCipher

All persistent app data lives in one Room database, BeefTechDatabase, stored in a SQLCipher-encrypted SQLite file. Schema version 47; BeefTechDatabase.VERSION is the source of truth.

  • DatabaseProvider.initialize(context, passphrase: ByteArray) is the single entry point. It returns a DatabaseResult and keeps one open instance for the process.
  • Workers call DatabaseProvider.getDatabase(). It is null until MainActivity has unlocked the database, so every worker returns Result.retry() in that case instead of failing.
  • DatabaseFactory.create builds the database with SQLCipher's SupportOpenHelperFactory and registers every migration.
  • Schemas are exported (exportSchema = true) to android/database/schemas/com.beeftech.database.BeefTechDatabase/ and committed.

The non-negotiable rules

Phones can hold unsynced data for days. Losing it is the worst failure this app can have; a real incident is written up in docs/database/incident-2026-09-r0-migration-data-loss.md.

Never lose field data
  • Never use fallbackToDestructiveMigration or any other destructive fallback. Every version step needs an explicit migration that keeps the data.
  • Values that cannot be mapped go into quarantine or legacy tables. Never drop them.
  • Backfill GUIDs before adding a unique index on them.
  • Never delete a local record because a sync failed. Mark it, keep it, retry.
  • The only deliberate deletion of unsynced data is the audited Day-7 policy wipe in SyncSecurityDao.

Keep DAO calls inside repository classes. ViewModels and UI never touch a DAO.

Changing the schema

Any change to an entity (new table, column, index, type) needs every one of these steps:

  1. Add or edit the entity in entity/ and its DAO in dao/. Add a new entity to the entities = [...] list and a DAO accessor on BeefTechDatabase.
  2. Bump BeefTechDatabase.VERSION by one.
  3. Add MIGRATION_n_n+1 to the BeefTechDatabase companion object. Write the SQL to match exactly what Room generates for the entity (column types, NOT NULL, defaults, index names); the exported schema JSON shows you the expected createSql.
  4. Register it in DatabaseFactory.kt's .addMigrations(…), wrapped in guarded(…), which turns any failure into a MigrationExecutionException.
  5. Build once so Room exports the new schema JSON, and commit it under android/database/schemas/…/.
  6. Add a migration test (next section).
  7. Run ./gradlew :android:database:connectedAndroidTest on an emulator.

A typical additive migration looks like this:

val MIGRATION_47_48 = object : Migration(47, 48) {
    override fun migrate(db: SupportSQLiteDatabase) {
        // Additive and idempotent where possible; existing rows keep their data.
        db.execSQL("ALTER TABLE `feed_crib_entries` ADD COLUMN `note` TEXT")
    }
}
Version 15Version 15 is deliberately unused; the chain goes 14→16. See the comment above MIGRATION_14_16.

Testing a migration

Migration tests live in android/database/src/androidTest/java/com/beeftech/database/ and use Room's MigrationTestHelper with the committed schema JSON. Copy Migration30To31Test.kt or Migration16To17Test.kt. A good migration test:

  • creates the database at the old version and inserts realistic rows, including unsynced ones;
  • runs the migration and validates the result against the new schema;
  • reads the rows back and checks that nothing was lost or changed by accident.

These tests need a real SQLite implementation, so they cannot run as JVM unit tests. CI runs them on an API 30 emulator (Chapter 9).

Deferred database follow-ups are tracked in docs/database/future-checks.md; the schema is drawn in docs/database/schema-diagram.svg.

Chapter 5Offline storage and sync

Life of a record

A record moves through a small set of states. Only the server's per-record answer moves it to SYNCED.

The pending_sync queue

PendingSync (entity/PendingSync.kt) is the cross-module queue: one row per record still to send, with entityType, entityId (the record GUID), operation, payload, createdAt, retryCount and the owning user_id. Use it through PendingSyncRepository:

CallUse it to
queueOperation(type, id, op, payload)Queue a record right after saving it
getPendingOperations() / getAllPendingOperations()Find what is waiting (the first respects the retry limit)
markSyncSuccessful(id) / markEntitySyncSuccessful(…)Clear the queue row once the server said SYNCED
markSyncFailed(id, …) / resetRetryCount(…)Count a failed attempt, or give a manual retry fresh attempts
observePendingCount(userId) / observeOldestPendingAt(userId)Drive the Home counts and the Day-7 policy

The queue also feeds the 7-day policy and the "waiting" counts on Home, so every synced record type must queue its records here, even if the feature also tracks sync_status on its own table. Newer features (feed crib) treat their own table as the source of truth and repair the queue whenever the two disagree.

Legacy rowsuser_id is nullable for rows created before database version 31. Those rows are deliberately not attributed to any user, because guessing could lock or wipe the wrong person's data.

Workers and the dispatcher

Each feature has a CoroutineWorker that sends its waiting records. SyncAllDispatcher.dispatch (in :demoapp) enqueues all of them as unique one-time work with a CONNECTED network constraint:

Unique work nameWorker
farmer-registration-syncFarmerSyncWorker
calf-registration-network-available-syncCalfRegistrationSyncWorker
treatment_network_available_syncTreatmentSyncWorker
animal-movement-scheduled-syncAnimalMovementSyncWorker
mortality-scheduled-syncMortalitySyncWorker
cost-scheduled-syncCostSyncWorker
traceability-outbox-scheduled-syncTraceabilityOutboxWorker

feed-crib-network-available-syncFeedCribSyncWorker

The dispatcher is triggered by:

  • Sync now on Home and Retry Sync in Traceability, with ExistingWorkPolicy.REPLACE (an explicit request restarts a running worker);
  • the 05:00 and 18:00 windows (ScheduledBatchSyncWorker), with KEEP so a worker already syncing is not started twice.

Each request carries a trigger (SyncRunSummary.TRIGGER_INPUT_KEY: morning, evening, manual or auto). Workers wrap their work in SyncRunRepository.trackRun(module, entityTypes, trigger) { … }, which records a row for the sync history screen.

A well-behaved worker:

override suspend fun doWork(): Result {
    val database = DatabaseProvider.getDatabase() ?: return Result.retry()   // not unlocked yet
    val tokens = TokenProviderRegistry.get() ?: return Result.retry()
    return try {
        syncRuns.trackRun(SyncRunModule.FEED, listOf(ENTITY_TYPE), trigger) { repository.syncPending() }
        if (stillWaiting()) Result.retry() else Result.success()
    } catch (e: Exception) {
        Result.retry()   // never delete a local record because sync failed
    }
}
Immediate sendSome features, such as feed crib, also try to send a record straight after saving it when the phone is online. That is only a shortcut; the worker remains the guarantee.

Batch names

Uploads carry an optional batch name in the format [FarmCode]-[Project]-[YYYYMMDD]-[HHMMSS]-[DeviceID], for example S001-FEED_CRIB-20261010-141503-emulator_5554.

  • The phone builds it with FileNamingUtils / BatchNaming in :android:database; the server's copy is common/FileNaming.kt. Keep the regex and the project codes in step on both sides.
  • Project codes: CALF_REG, FARMER_REG, TREATMENT, MOVEMENT, MORTALITY, COST, TRACE_EVENT, FEED_CRIB, REPORT.
  • The server (SyncUploadLog.problemWith) rejects a present name with 400 if the format is wrong, the project does not match the endpoint, the farm code is not the caller's site, or the device is not the signed-in device. A missing name is accepted as a legacy upload.
  • Every upload is logged in sync_upload_log; a retry with the same name updates its row.

What the server does with a batch

  1. Authenticates the caller and reloads their role, site and device from the database.
  2. Checks the batch name (call.acceptBatch(principal, ProjectCode.X, request.batchName)).
  3. Validates each record on its own. A bad record gets status = "ERROR" with a message and does not stop the rest of the batch.
  4. Upserts each good record by its GUID, so a retry can never create a duplicate. The submitter and site come from the token, never from the request body.
  5. Logs the upload (SyncUploadLog.record) and answers with one result per record.

The phone then marks each SYNCED result as synced (using the server's serverSyncedAt when given), clears its queue row, and keeps every ERROR record with its message for the user to see.

The 7-day policy

If a user's data stays unsynced, the app escalates. SyncPolicyEnforcer evaluates the age of the oldest pending record per user; SyncPolicyGate runs it every 60 seconds in the app and SyncPolicyActivityGuard applies a lock in every Activity.

Age of oldest unsynced recordWhat happensWho can change it
Days 2, 4 and 6 (defaults)Warnings of increasing severityAdmins, via PUT /api/sync-policy (days 1–6)
Day 7Pending local operations are wiped and the account is locked, both auditedNobody. SyncWarningPolicy.WIPE_DAY = 7 is a constant the server cannot move
After a lockThe user can only sign in to report the lockAn admin clears it: POST /api/users/{id}/clear-sync-lock
Be careful hereThis is the one place the app deletes unsynced data on purpose. Any change to SyncPolicyEnforcer, SyncWarningPolicy or SyncSecurityDao needs tests for the boundary days and for users who share a phone.

Device check-in

DeviceCheckInWorker runs after each online sign-in, including for a locked account (after a wipe that is the only time a valid token exists). Each step is independent and the job is retried if any fails:

  • pulls reference data (ReferenceDataSync, using ?ifVersion= to skip unchanged data);
  • pulls the sync-warning policy (SyncPolicySync) and the site's feed cribs;
  • uploads the phone's sync security events (SecurityEventSync);
  • lifts the phone's Day-7 lock once an admin has cleared it on the server (SyncLockRelease).

It never reads or writes pending_sync, so it cannot block or reorder a sync.

Chapter 6Authentication and security

Online sign-in

Users sign in with a username and a 5-digit PIN. AuthRepository (in :android:authentication) posts to POST /api/auth/login with the username, PIN and device ID (and optionally the device model and app version).

ResponseMeaning
200A JWT (HMAC256, 24 h) and the user, including the BCrypt PIN hash the phone caches for offline sign-in
401Wrong username or PIN
409The user is bound to a different device
403This device has been revoked
423Locked: 5 wrong PINs lock the account on the server for 5 minutes

The first successful sign-in binds the user to that device (users.device_assigned_id). A manager can unbind it.

Offline sign-in

With no network, AuthRepository checks the PIN against the cached BCrypt hash (BCrypt.checkpw). A user must have signed in online once on that phone first. A successful offline sign-in gives local access only for up to seven days: SessionStore.saveOffline keeps that window separate from the real JWT expiry, and no token is invented for the server.

On the phone, PinLockoutManager blocks further attempts for 1 minute after 5 wrong PINs. This is separate from the server's 5-minute lock.

Sessions and tokens on the phone

  • SessionStore is the interface; EncryptedSessionStore stores the JWT, user and expiry in encrypted preferences. It also implements TokenProvider.
  • TokenProviderRegistry and CurrentUserIdRegistry (in :android:database) let any module get the token or current user without depending on :android:authentication.
  • API clients call tokenProvider.token() and attach it with bearerAuth(token).
  • On a 401, a client calls tokenProvider.reportUnauthorized(body). The session store decides what that means (expired, revoked, deactivated) and ends the session; the user lands on the login screen. Queued records are never touched.

Checking a request on the server

There is no Ktor authenticate { } block. Each handler calls one of the helpers in AuthUtils.kt as its first line:

HelperReturns / does
call.requireAuthPrincipal(jwtService)The caller's AuthPrincipal, or responds 401 and returns null
call.requireRole(jwtService, Role.ADMIN, Role.MANAGER)Same, plus 403 if the role is not listed
call.requireBearerToken(jwtService)Only the username; same checks

The check runs in a fixed order: decode and verify the JWT; check the live account and device state (inactive user, revoked device, PIN reset after the token was issued → 401); then reload role, site and device from the user row. So deactivations, role changes and site moves apply on the very next request, even with an older token.

post("/api/things/sync") {
    val principal = call.requireAuthPrincipal(jwtService) ?: return@post
    ...
}

Record scope

Reads are scoped by role through RecordScope (RecordScope.kt):

RoleScopeSees
AdminRecordScope.AllEverything
ManagerRecordScope.Site(siteId)Their site's records. A manager without a site sees nothing
Worker, or unknown roleRecordScope.User(userId)Only their own records

Use it in every list, single-record read and dashboard count, and pass the table's voided_at column so voided records stay hidden:

Table.selectAll().where {
    principal.recordScope().predicate(Table.submittedByUserId, Table.siteId, Table.voidedAt)
}

Before production

Development defaults to remove
  • Set BEEFTECH_JWT_SECRET. Without it the server falls back to a fixed dev secret and prints a warning.
  • Turn off the dev seed (BEEFTECH_SEED_DEV=false); the Render blueprint currently turns it on.
  • Replace the demo SQLCipher passphrase with the KeyStore-backed key, with a re-key migration for installed phones.
  • Remove usesCleartextTraffic="true" from release manifests.
  • Stop returning pin_hash in the login response, or protect what the phone stores, as part of a reviewed offline-login design.

Chapter 7The backend

Code layout

All server code is in backend/api/src/main/kotlin/com/beeftech/backend/api/. Each feature is a set of flat files with a common suffix.

FileResponsibility
*Routes.ktA fun Route.xRoutes(jwtService, service) extension. Authenticates, parses, calls the service, responds with ApiResponse
*Service.ktValidation and business rules; per-record results for sync
*Repository.ktExposed queries inside newSuspendedTransaction(Dispatchers.IO, db = DatabaseFactory.getDatabase())
*Table.ktExposed Table objects (the schema)
*Models.kt@Serializable request and response DTOs
*SchemaMigration.ktIdempotent changes to tables that already exist

Sub-packages: auth/ (login, JWT, users, sites, devices, login security, dev seed), feedCrib/ (package …api.feedcrib) and common/ (ApiResponse, FileNaming). Shared helpers: AuthUtils.kt, RecordScope.kt, SyncUploadLog.kt, PdfGenerator.kt, ReportCsv.kt, CalfPhotoStore.kt.

Start-up

Application.kt holds main(), which starts Netty on $PORT (default 8081), and Application.module(), which:

  1. resolves the JDBC URL and calls DatabaseFactory.init(jdbcUrl) (Database.kt): runs the schema migrations, then SchemaUtils.create(…) for every table, then seeds reference data and feed crib codes;
  2. installs ContentNegotiation with Json { ignoreUnknownKeys = true }, so a newer app sending extra fields keeps working against an older server;
  3. seeds the dev site, users and cribs if the dev seed is on;
  4. builds the repositories and services by hand (there is no DI framework) and registers every route group inside routing { }.

Tests call the same module(), so anything you wire here is exercised by the route tests.

Server schema changes

SchemaUtils.create only creates tables that are missing; it never alters an existing one. So:

  • A new table: define the Table object and add it to the SchemaUtils.create(…) list in Database.kt.
  • A new column on an existing table: add it to the Table object and write a *SchemaMigration object that adds it with ALTER TABLE when PRAGMA table_info shows it is missing. Call it in DatabaseFactory.init before SchemaUtils.create. Follow RecordVoidSchemaMigration.kt: idempotent, and a no-op when the table does not exist yet.
  • Add a *SchemaMigrationTest that starts from the old shape and checks existing rows survive.

Anatomy of a route

The feed crib sync endpoint shows every convention in a few lines:

/* Submitter and site come from the token, never the body. */
post("/api/feed-crib-entries/sync") {
    val principal = call.requireAuthPrincipal(jwtService) ?: return@post
    val request = call.receive<FeedCribEntrySyncRequest>()

    if (!call.acceptBatch(principal, ProjectCode.FEED_CRIB, request.batchName)) return@post

    val response = feedCribService.sync(request, principal.userId, principal.siteId)
    SyncUploadLog.record(principal, ProjectCode.FEED_CRIB, request.batchName, response.results.map { it.status })

    call.respond(ApiResponse(success = true, message = "Feed crib entries synchronized.", data = response))
}

Every response body is an ApiResponse<T>(success, message, data), including errors.

Voiding, audit, email, reports

  • Voiding is the only way to correct a synced record; there are no edits. POST /api/records/{type}/{id}/void sets voided_at, voided_by_user_id and void_reason and writes the audit log. A new record type that managers should be able to void needs those columns and an entry in VoidRepository.
  • Audit log (AuditLogTable): written with insertAuditRow(…) by user, site, device, login security, reference data, sync policy, void and restore changes; read through AuditService.
  • Email (FarmerSalesNotification.kt): the first sync of a farmer, and of a calf registration, emails a JSON receipt to the site's sales rep (or BEEFTECH_SALES_REP_EMAIL). A farmer is emailed at most once (claimed via farmers.sales_notified_at). With incomplete SMTP settings the email is logged instead and retried on a later sync.
  • Reports (ReportService, ReportCsv, PdfGenerator with PDFBox): JSON, CSV or PDF via ?format=. Calf birth certificates are PDFs too.
  • Photos (CalfPhotoStore): raw image/jpeg, max 5 MB, stored on disk under the media folder.

Android unit tests

Feature logic is tested on the JVM with hand-written fakes rather than a mocking library. android/feed-crib/src/test/ is the model:

  • fakes/FakeFeedCribDao.kt and FakePendingSyncDao.kt — in-memory DAOs;
  • fakes/FakeFeedCribServer.kt — a scriptable backend behind Ktor's MockEngine, with an offline switch;
  • fakes/FakeTokenProvider.kt — a token source;
  • FeedCribRepositoryTest, FeedCribViewModelTest, FeedCribApiClientTest, SlotAllocatorTest.

Because repositories take their clock, time zone and user ID as constructor parameters, tests can pin the time of day and the signed-in user. Modules that log through android.util.Log set unitTests.isReturnDefaultValues = true so logging does not throw on the JVM.

Test what matters for field data: a save survives a failed sync; a retry does not duplicate; an ERROR result is kept and shown; the queue and the record table agree afterwards.

Backend route tests

Backend tests start the real module() in Ktor's testApplication against a fresh temporary SQLite file, with the dev seed on. Helpers live in AdminTestHelpers.kt:

@Test
fun `a worker sees only their own records`() = testApplication {
    startAdminApp()                                  // temp DB + dev seed + module()
    val client = createClient { }
    val worker = client.adminLogin("jvdm", "30003")  // returns a JWT
    val response = client.adminSend("GET", "/api/treatments", worker)
    assertEquals(HttpStatusCode.OK, response.status)
}

Pass the same file to startAdminApp(file) twice to simulate a restart on the same database (useful for schema migrations).

Flaky suite:backend:api:test is known to be flaky: a different single test can fail on each run, probably because tests share static state (N5 in docs/database/future-checks.md). Re-run before assuming a regression, and do not add new shared mutable state.

FarmerSalesNotificationLiveTest sends a real email and is skipped unless BEEFTECH_SMTP_LIVE_TEST=true.

Chapter 10Recipes

Adding a new synced record type

The most common large change. Feed crib (schema 47) went through every step below; read its files next to this list.

On the server

  1. Table. Create XTable.kt with a unique record_guid, the record's fields, submitted_by_user_id, site_id, device_id, capture and server-sync timestamps, and voided_at / voided_by_user_id / void_reason if it can be voided. Add it to SchemaUtils.create(…) in Database.kt.e.g. feedCrib/FeedCribTable.kt
  2. Models. @Serializable sync request (deviceId, batchName?, records), per-record result (recordGuid, status, message?, serverSyncedAt?) and response.
  3. Repository. upsert by GUID inside newSuspendedTransaction; scoped list and single reads using RecordScope.predicate(…).
  4. Service. Validate each record; return SYNCED or ERROR per record, never throw for the batch.
  5. Project code. Add a value to FileNaming.ProjectCode (server) and the phone's copy in :android:database.
  6. Routes. POST /api/x/sync following the anatomy above, plus GET reads. Register them in Application.module().
  7. Tests. A XRoutesTest covering: unauthenticated → 401, upsert is idempotent, submitter/site come from the token, one bad record does not fail the batch, scope per role, bad batch name → 400.

On the phone

  1. Entity and DAO in :android:database, with record_guid as the key, sync_status, sync_error, synced_at, user_id, device_id, captured_at. Index sync_status.
  2. Migration: the full checklist in Chapter 4, including the schema JSON and a migration test.
  3. API client in the feature's data/: baseUrl = BackendConfig.baseUrl, bearerAuth(token), report 401, return Result<T>. Send a batch name.
  4. Repository: save locally → queueOperation(ENTITY_TYPE, guid, "UPSERT", …) → try syncPending(). Apply results per record; clear the queue row only on SYNCED.
  5. Worker: the shape in Chapter 5, wrapped in SyncRunRepository.trackRun. Add a SyncRunModule value if the feature is new.
  6. Dispatcher: add a unique work name and the worker to SyncAllDispatcher, and update its test in demoapp/src/test/.
  7. Home and policy: make sure the pending count on Home and the 7-day policy see the new entity type (they read pending_sync).
  8. UI: ViewModel + screens; a tab in AppTab or an entry from an existing screen.
  9. Tests: repository and ViewModel tests with fakes (Chapter 9).
  10. Docs: README module table and API reference, this manual, the User Manual.

Adding an endpoint

  1. Add the DTOs to the feature's *Models.kt.
  2. Add the query to the repository and the rule to the service.
  3. Add the route to the feature's *Routes.kt. First line: requireAuthPrincipal or requireRole. Use RecordScope for reads. Respond with ApiResponse.
  4. If it is a new route group, register it in Application.module().
  5. Write route tests for each role (allowed and refused).
  6. Add a method to the Android API client that will call it, and add the endpoint to the README and Chapter 8.

Adding a manager or admin screen

Management screens in :android:management are online-only: they call the server through ManagementApiClient and show a "needs connection" notice when offline. They do not write to Room or pending_sync.

  1. Add the call to ManagementApiClient (management/data/).
  2. Add a ViewModel in management/viewmodel/ exposing loading, content, error and offline states.
  3. Add the screen in management/ui/. Admin-only pages go inside the Admin area; manager pages get an AppTab value and an entry in moreTabsFor.
  4. Protect the endpoint on the server with requireRole; never rely on the screen being hidden.
  5. Add ViewModel tests in android/management/src/test/.

Adding a dependency

  • Add it to gradle/libs.versions.toml and reference it as libs.…. Older modules still hard-code coordinates; new code should use the catalog.
  • Repositories can only be declared in settings.gradle.kts (FAIL_ON_PROJECT_REPOS).
  • Match the Ktor client version (3.0.3) and Compose BOM already used by the module you are editing.
  • If the dependency brings SQLCipher or BouncyCastle into a new module, copy the packaging { resources { excludes += … } } block from :android:database to avoid duplicate META-INF errors.

Chapter 11Building, releasing and deploying

Building the APK

./gradlew :demoapp:assembleDebug     # → demoapp/build/outputs/apk/debug/
./gradlew :demoapp:assembleRelease   # talks to https://beeftech-backend.onrender.com/
  • applicationId is com.beeftech.demoapp, versionName 1.0; bump versionCode and versionName in demoapp/build.gradle.kts for each release so phones accept the update.
  • No release signing config is committed. Sign release APKs with the team's keystore outside the repository; never commit it.
  • On phones the app is still labelled demoapp in the app drawer.
  • An update must open the existing encrypted database and migrate it. Test an upgrade over the previous release with unsynced data on the phone before shipping.

Deploying the backend

The Dockerfile builds :backend:api:installDist on Temurin 17 and runs /app/bin/api on a JRE 17 image, exposing 8081. render.yaml deploys it to Render as beeftech-backend:

  • auto-deploys on every commit to the tracked branch; health check /health;
  • generates BEEFTECH_JWT_SECRET; SMTP goes through the Brevo relay; BEEFTECH_SMTP_USERNAME, _PASSWORD, _FROM and BEEFTECH_SALES_REP_EMAIL are entered in the Render dashboard (sync: false) and never committed;
  • BEEFTECH_SEED_DEV=true, so the dev users exist on the hosted server.
No persistent diskThe Render service has no disk, so the hosted SQLite database and calf photos reset on every redeploy or restart. Treat it as a demo environment. Production needs a persistent volume (and BEEFTECH_DB_URL / BEEFTECH_MEDIA_DIR pointing at it) or a managed database.

To try the image locally:

docker build -t beeftech-backend .
docker run -p 8081:8081 -e BEEFTECH_SEED_DEV=true -e BEEFTECH_JWT_SECRET=dev-only beeftech-backend

Known gaps

  • The demo SQLCipher passphrase, the JWT fallback secret and the dev users are hard-coded for development.
  • usesCleartextTraffic="true" is set in main manifests, so release builds allow HTTP too.
  • The login response includes the user's pin_hash (used for offline sign-in).
  • The Render deployment has no persistent disk and seeds the dev users.
  • CalfRegistrationViewModel and TreatmentViewModel re-enqueue the legacy 15-minute periodic jobs that ScheduledSyncScheduler cancels.
  • The biometric prompt code in :android:authentication is unused.
  • backend/authentication, backend/sync, docs/architecture/ and docs/testing/ are empty.
  • backend/api/requests.http is stale; stale standalone Gradle files remain under android/.
  • Dependency declarations are mixed between the version catalog and hard-coded coordinates; Compose BOM versions differ between modules.
  • CI jobs are not required checks; :backend:api:test is flaky.
